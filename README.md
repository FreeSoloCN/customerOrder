# 工单值班台

客服工单趋势分析工具。主管把工单文件拖进页面，立刻拿到一份带结论、判断依据和工单号的报表——不用装软件，不用找人跑脚本，也不需要懂技术。

纯前端单页，没有后端。**工单数据只在浏览器本地解析，不会上传到任何服务器**，这一点对含客户原话的工单尤其重要。

## 怎么用

1. 打开页面（部署到 GitHub Pages 后就是一个网址）。
2. 把 `tickets.json` 拖进去，或点「选择文件」。第一次可以先点「先看示例数据」，一秒钟看到长什么样。
3. 从上往下看：最上面是**需要你过问的几件事**，下面是支撑这些结论的图表，最后是可筛选的工单明细。异常卡里的工单号可以点，会跳到明细并高亮。

文件读不了时页面会说清楚是哪一条工单、哪个字段有问题，而不是白屏或报一句「解析失败」。

## 分析维度

选维度的标准只有一个：这个角度能不能改变主管今天的动作。

| 维度 | 算什么 | 对主管的价值 |
|---|---|---|
| 时间趋势 | 每天工单量、当天未解决数、当天平均满意度 | 量在涨、满意度在掉是最需要警惕的组合，能第一时间发现「出事了」 |
| 类型分布与变化 | 各分类占比，以及把周期对半切后前后两段的**日均**工单量 | 知道人力该往哪压；用日均而不是总量，两段天数不等也不会误判 |
| 严重程度 | 各优先级的平均处理时长、解决率、满意度 | 检验「高优先级」这个标签有没有真的换来更快的处理，而不只是个标记 |
| 处理效率与满意度的关联 | 每张工单的时长×满意度散点，以及时长中位数 | 区分「慢但客户能接受」和「又慢又炸」，后者才是要立刻捞出来的 |
| 渠道差异 | 各渠道的量、时长、满意度、未解决数 | 判断是渠道本身体验差，还是难题都被转到了这个渠道 |
| 问题指纹 | 用关键词把工单描述归到同一个具体问题上 | 分类标签只说「支付问题」，指纹告诉你具体是「重复扣款」还是「扣款成功但订单没生成」——前者退钱，后者得让技术改系统 |

## 异常识别规则

阈值是固定的，主管不需要配置。每条异常在页面上都会写明触发的依据和涉及的工单号，可以点开核对客户原话。

| 规则 | 触发条件 | 级别 |
|---|---|---|
| R1 某类工单激增 | 后半段日均 ≥ 前半段 1.5 倍且后段 ≥3 张 → 关注；≥2 倍 → 严重 | 严重 / 关注 |
| R2 同一问题反复出现 | 同一问题指纹命中 ≥3 张 → 关注；≥5 张 → 严重 | 严重 / 关注 |
| R3 高优先级积压 | 优先级为高且未解决；≥3 张 → 严重 | 严重 / 关注 |
| R4 分类满意度垫底 | 某分类样本 ≥3 张且平均满意度 ≤2.0 分 | 关注 |
| R5 满意度下滑 | 后半段平均满意度比前半段低 ≥0.4 分 | 关注 |
| R6 又慢又差 | 处理时长 ≥ 中位数的 3 倍，且满意度 ≤2 分 | 留意 |
| R7 渠道差距 | 满意度最高与最低的渠道相差 ≥0.5 分 | 留意 |

几个刻意的取舍：用**日均**而不是总量做环比，避免被不等长的时间段带偏；用**中位数**而不是平均值定义「慢」，避免被一两张 120 小时的单子抬高门槛；「留意」级默认折叠，不跟真正紧急的事抢注意力。

## 示例数据（50 张工单，6 月 1–11 日）发现了什么

**支付问题在后半段翻了一倍还多。** 6 月 7–11 日共 11 张，日均 2.2 张；6 月 1–6 日只有 5 张，日均 0.83 张，涨幅 164%。它已经从第三多的分类变成占比 32% 的头号来源。

**而且不是同一种支付问题，是三种，都指向系统而不是客服。** 一是重复扣款和金额不对，6 张（T012、T022、T030、T037、T046、T050），其中 T046 客户明说「又出现重复扣款了，上个月也有过」；二是扣款成功但订单状态没跟上，6 张（T008、T020、T028、T032、T035、T041），典型说法是「显示扣款成功但订单还是待支付」，T035 甚至已经影响发货；三是退款迟迟不到账，6 张。这类问题客服回一百遍也止不住来单，需要转给支付和订单团队。

**7 张高优先级工单还挂着，平均已经压了 55.7 小时。** 最久的 T031 已经 120 小时——客户垫付的退货快递费说好要退，一直没退。这 7 张的满意度全是 1 分。

**高优先级并没有被优先处理。** 高优先级 31 张，平均 26.8 小时、解决率 77%、满意度 1.87 分；低优先级 6 张，平均 1.4 小时、解决率 100%、满意度 4.0 分。优先级标签目前更像是问题严重性的记录，而不是处理顺序的依据。

**满意度在掉。** 前半段平均 2.75 分，后半段 2.00 分，掉了 0.75 分。6 月 8 日单日只有 1.4 分。整体 50 张里有 27 张打了 1–2 分。

**退款退货是体验最差的分类**：13 张、平均 45.2 小时、满意度 2.0 分、5 张未解决。其中退货运费谁承担的争议独立出现了 4 次（T011、T021、T031、T042），这是一条规则不清楚、而不是执行不到位的信号。

**投诉全是 1 分，且 4 张里有 3 张在投诉客服本身**：态度差（T010）、等 40 分钟才有人接（T034）、机器人反复答非所问（T026、T044）。

**电话渠道体验明显差一截**：16 张、满意度 1.94 分、平均 31.6 小时；在线 34 张、2.56 分、14.1 小时。需要先确认是渠道本身的问题，还是难题都被升级到了电话。

一句话给主管：**今天最该做的一件事，是把支付类工单的原话打包给技术团队，同时把那 7 张挂着的高优先级工单逐张清掉。**

## 部署到 GitHub Pages

仓库里只有静态文件，没有构建步骤。

1. 把本目录推到 GitHub 仓库。
2. 仓库 Settings → Pages → Source 选 `Deploy from a branch`，分支选 `main`、目录选 `/ (root)`，保存。
3. 一两分钟后访问 `https://<用户名>.github.io/<仓库名>/`，把网址发给主管即可。

`index.html` 是自包含的单文件（CSS、JS、示例数据全部内联），只从 CDN 引入 Chart.js 画图。

## 数据格式

`sample-data/tickets.json` 是示例，`sample-data/ticket_fields.md` 是字段说明。文件需要是工单对象组成的 JSON 数组：

```json
[{
  "ticket_id": "T001",
  "created_at": "2024-06-01 09:15",
  "category": "退款退货",
  "description": "退货申请提交一周了还在审核中",
  "priority": "高",
  "resolution_time_hours": 72,
  "satisfaction": 2,
  "channel": "在线",
  "is_resolved": true
}]
```

页面会逐条校验时间格式、优先级取值、满意度范围等，跳过不合规的记录并把原因列出来。所有维度都从数据里动态推导——换一批分类名、渠道名或时间范围，页面照样跑，不需要改代码。

## 文件说明

```
index.html                     单文件应用，部署时只需要它
sample-data/tickets.json       50 条示例工单
sample-data/ticket_fields.md   字段说明
build/app.js                   分析引擎与渲染逻辑源码
build/index.template.html      页面模板
build/build.py                 把模板 + 源码 + 示例数据合成 index.html
build/verify.js                校验脚本：跑通分析与渲染，核对各项统计
```

改代码时编辑 `build/app.js` 或 `build/index.template.html`，然后运行 `python3 build/build.py` 重新生成 `index.html`。

## AI 工具使用情况

整个工具由 Claude（Opus 5，在 Claude 桌面端的 agent 模式下）完成，人给方向、做取舍和验收。

分工大致是这样：先用 Claude 把 50 条工单过了一遍，看清时间跨度、分类分布、未解决工单的集中位置和描述里的重复措辞，**异常规则的阈值是照着真实数据的量级定的，不是拍脑袋写的常数**（比如用中位数 7 小时而不是平均值 19.7 小时定义「慢」）。问题指纹的关键词表也是从 50 条真实描述里归纳出来的。方案形态经过一轮调整：最初计划用 Python 离线跑出结果再嵌进静态页，讨论后改成主管自己上传、浏览器里实时分析，分析逻辑因此从 Python 搬到 JS，只维护一份代码。

验证环节没有偷懒：用 Python 独立算了一遍所有统计量，和页面 JS 的输出逐项比对；又在 Node 里用 DOM 桩把渲染流程真跑了一遍，确认没有运行时错误、生成的 HTML 结构完整、筛选和搜索都有正确结果。`build/verify.js` 保留了这套校验，改完代码可以直接重跑。

需要说明的是，所有数字结论都来自这 50 条数据的直接计算，AI 没有参与生成或推测任何数据。

## 已知局限

样本只有 50 条、11 天，环比用的是「前后对半切」而不是同比，遇到周末效应或大促这类周期性波动会失真，数据量大了之后更适合改成按周对比或对比上一个同长度周期。问题指纹依赖中文关键词表，换一个行业需要替换词表；如果工单量级到了几千条以上，这里更适合换成聚类或向量相似度。满意度只有已评分的工单才有，未评分工单的沉默偏差没有纳入考虑。
